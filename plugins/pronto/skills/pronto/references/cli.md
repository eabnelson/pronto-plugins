# Pronto local CLI

## What the CLI is for

The `s4` CLI is for this device: installing and updating itself, signing in, and connecting and running a messaging channel (iMessage or WhatsApp) on a Mac. Do all workspace work (reading, saving, posting, sharing, Apps, administration, approvals, external connections) through the connected Pronto tools, not the CLI. Workspace commands such as `context create`, `actions invoke`, `artifacts download` and `connections` were removed and answer `command_removed`. An always-on Agent uses its own Agent credential from a setup link, not the CLI. Never ask the user to paste an access token, refresh token, authorization code, or credential into the conversation.

## Start once per device task

1. Resolve the absolute `s4` executable path once and use that path for every command in this task. If `s4` is missing, download `https://pronto.ooo/install.sh` over HTTPS, inspect that it resolves release metadata only through Pronto, downloads the binary from public R2, and verifies byte length plus SHA-256 before replacement. Run it and retain the reported path (`${S4_INSTALL_DIR:-${XDG_BIN_HOME:-$HOME/.local/bin}}/s4` on POSIX or `%LOCALAPPDATA%\StudioFour\bin\s4.exe` on Windows). On Windows use `https://pronto.ooo/install.ps1`. Do not assume the install directory is already on `PATH`.
2. Run `<s4-path> health --json --compact`. Continue when `status` is `compatible`. If it is `update_available` or `update_required`, run `<s4-path> update --json --no-input` once for this task. On Windows, a staged update activates after the updater exits; poll `<s4-path> --version` for at most 30 seconds until it matches `latestCliVersion`. Then run health once more. If health still requests an update, stop and report the executable path plus installed and expected versions; never repeat the download loop.
3. If a command reports `authentication_required` or `authentication_expired`, run `<s4-path> login --json --no-input`. This starts remote device authorization: relay the non-secret verification URL and short human code printed by the CLI, tell the user they may open it on any device, and wait for the command to complete. Never ask for the resulting token, never paste a credential into chat, and never repeat login in a loop. On an attended graphical machine, `s4 login` without `--no-input` may use the local system browser and loopback callback instead.

## Connect a messaging channel

- Treat messaging channels as a separate setup surface from external provider connections. A channel is where people message the Studio (the app itself, iMessage); a connection is an account its agents use (GitHub). When the user asks to connect one without specifying preferences, run `<s4-path> channels connect --json --compact` on the Mac that will host it. It safely defaults to personal Messages and handle-only activation through `@s4`; `--account-mode dedicated` changes identity handling, while every direct and group message still requires the configured handle. When setup reports `needs_human_action` with `action: enable_studio_connection` (or `installed` with that required action), the device is connected but not yet enabled for a Studio: enable it yourself by invoking `channel.settings.update` through the connected Pronto tools (`invoke_action`) in the target Studio, with `payload.scope: "studio_binding"`, the reported `connectionId`, `guestGroupPolicy`, `entryPolicy` (default `closed`), and the `handle` tag the user chose (default `@s4`); show the user the device, Studio, and tag first, and never send them to a browser or console for this step. If the tools are not connected in this session, ask the user to connect the plugin or `https://pronto.ooo/mcp` and do it there. Use `channels catalog` only when the user asks to see available choices. Stop before authentication when the CLI reports `channel_host_platform_unsupported`. Immediately execute the returned `data.next` command and each subsequent setup command in the same task, replacing its `s4` executable with the resolved absolute path. Fill machine-discoverable fields locally and pause only for the single `s4 login` device authorization, macOS permission approval, or information that cannot be discovered safely. Untagged messages never invoke the agent. Connecting a channel needs exactly one owner sign-in: setup derives the channel host's own narrower credential from the `s4` login, so never expect, request, or relay a second device code, and never copy credentials between the two. If a `channels host` command or setup reports `authentication_required`, run `s4 login --no-input` once and rerun it. If it reports `authentication_failed`, follow its remediation; on a signed-in Mac that is `s4 channels host login`, which re-derives the host credential from the same sign-in without a new code. `s4 update` does the same re-derivation itself. Stale host credentials from an earlier setup are replaced automatically; only `channel_host_credential_stale` needs the owner to delete `studio-four-channel-host` items in Keychain Access. The device-code form of `s4 channels host login` is a fallback for the dedicated `s4-channel-host` executable with no `s4` sign-in and is not part of the ordinary flow. The always-on Messages process retains a dedicated executable identity for macOS permissions even though setup is driven through `s4`. In groups, the verified sender is the actor and every participant is the disclosure audience, so an unresolved participant must fail closed before Studio discovery or agent execution.
- WhatsApp is a second channel on a Mac that already runs the channel host. It always uses the owner's own WhatsApp account. Run `<s4-path> channels connect --provider whatsapp --account-mode personal --json --compact` there; the explicit personal flag also works on older CLI releases. Setup prints a QR code on stderr for the user to scan from that phone under WhatsApp → Settings → Linked devices; pass `--phone <+number>` to get a pairing code instead. Linking is a human step: pause for it, never ask the user to send you the code. An existing pairing is reused. Enabling the connection for a Studio is the same `channel.settings.update` step as for iMessage. The owner's tagged messages activate in direct chats and Message yourself. `whatsapp_host_not_installed` means run plain `channels connect` on that Mac first. WhatsApp groups are not admitted until a later Pronto release; say so instead of retrying.
- Run `<s4-path> channels preflight --json --compact` before connecting a new Mac or after any surprising setup result. It is read-only and masked, contacts no service, and reports the route and rule setup would choose or the one decision still needed.
- Read channel setup results, never the binary. `needs_owner_decision` with `reason: routing_destination_ambiguous` means the role is settled but this Mac has used more than one phone number or email for the account: show `destinations[].destinationHandle` verbatim, ask which to send from, and rerun the returned `retry` command with `--destination-handle <choice>`. `routing_destination_missing` means this Mac has never sent from a routable handle: ask the user to send one iMessage from it, then rerun `retry`. `account_role_ambiguous` or `account_identity_conflict` ask for `--account-mode personal|dedicated` instead. A personal account with exactly one observed phone number needs no prompt; setup picks the phone. `retriable_failure` and `terminal_failure` carry a stable `reason`, a `remediation` sentence, and the exact `retry` command; follow them rather than inventing flags. Unknown options are rejected with `unknown_flag:<name>`, so a rejected command means a typo, not a missing feature.
- One Apple ID may be connected from several Macs; run `channels connect` on each. To stop one Mac, retire that device's connection with `channel.settings.update` through the Pronto tools (`status: "retired"`). Never use `connection.disconnect` for messaging channels; it is provider-wide and is refused with `channel_provider_device_scoped`.
- With `login --no-input --json`, the first stdout line is `data.status: "authorization_pending"` with the code and URL. Present it to the user at once; the command blocks until approval.
- `s4 update` on a Mac with a channel host re-derives the host credential and restarts the host. A host under signed maintenance may adopt the new release itself and exit right after the restart; launchd brings it back within about 30 seconds, so `launchctl list` can briefly show `-` for its PID. Check again after a minute before restarting it by hand with `launchctl kickstart gui/$(id -u)/com.studiofour.channel-host`.
- Requests the host could not finish are listed by `<s4-path> channels requests list`. `channels requests retry --event <id>` queues one retry of a proven pre-execution failure, and `channels requests manual-completed --event <id> --receipt <provider-id>` records one already answered by hand. `<s4-path> channels doctor` diagnoses the host without changing it.

## Failure behavior

Use the CLI error's `retryable` and `remediation` fields. Retry a retryable request once. Stop on release-verification, credential-store, authorization, or repeated service failures and report the safe remediation without printing raw headers, OAuth responses, or credentials.

Channel setup results and `<s4-path> help --json` are self-describing; do not copy their evolving schemas into this skill.
