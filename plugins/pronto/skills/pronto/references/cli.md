# Pronto local CLI

## What the CLI is for

The `s4` CLI is for this device: installing and updating itself, signing in, and checking and repairing a Mac's Channel Host, which answers iMessage and WhatsApp. Do all workspace work (reading, saving, posting, sharing, Apps, administration, approvals, external connections) through the connected Pronto tools, not the CLI. Workspace commands such as `context create`, `actions invoke`, `artifacts download` and `connections` were removed and answer `command_removed`. An always-on Agent uses its own Agent credential from a setup link, not the CLI. Never ask the user to paste an access token, refresh token, authorization code, or credential into the conversation.

## Start once per device task

1. Resolve the absolute `s4` executable path once and use that path for every command in this task. If `s4` is missing, download `https://pronto.ooo/install.sh` over HTTPS, inspect that it resolves release metadata only through Pronto, downloads the binary from public R2, and verifies byte length plus SHA-256 before replacement. Run it and retain the reported path (`${S4_INSTALL_DIR:-${XDG_BIN_HOME:-$HOME/.local/bin}}/s4` on POSIX or `%LOCALAPPDATA%\StudioFour\bin\s4.exe` on Windows). On Windows use `https://pronto.ooo/install.ps1`. Do not assume the install directory is already on `PATH`.
2. Run `<s4-path> health --json --compact`. Continue when `status` is `compatible`. If it is `update_available` or `update_required`, run `<s4-path> update --json --no-input` once for this task. On Windows, a staged update activates after the updater exits; poll `<s4-path> --version` for at most 30 seconds until it matches `latestCliVersion`. Then run health once more. If health still requests an update, stop and report the executable path plus installed and expected versions; never repeat the download loop.
3. If a command reports `authentication_required` or `authentication_expired`, run `<s4-path> login --json --no-input`. This starts remote device authorization: relay the non-secret verification URL and short human code printed by the CLI, tell the user they may open it on any device, and wait for the command to complete. Never ask for the resulting token, never paste a credential into chat, and never repeat login in a loop. On an attended graphical machine, `s4 login` without `--no-input` may use the local system browser and loopback callback instead.

## Messaging channels on a Mac

- To turn on iMessage or WhatsApp, use Pronto for Mac (download when available), or `<s4-path> channels connect`. Pronto for Mac, at `https://pronto.ooo/download` once its first release is published, signs in, guides the macOS permissions for iMessage, links WhatsApp with a QR or pairing code, and sets each channel's tag and Agents. Until then, run `<s4-path> channels connect --json --compact` on the Mac signed in to Messages (add `--provider whatsapp --account-mode personal` for WhatsApp, which prints a QR code on stderr to scan under WhatsApp → Settings → Linked devices, or a pairing code with `--phone <+number>`), run each returned `data.next` and `retry` command in order, and pause only for sign-in, macOS permission, linking, or a decision the output names. When it reports `enable_studio_connection`, invoke `channel.settings.update` through the connected Pronto tools with `payload: { scope: "studio_binding", connectionId: <reported id>, guestGroupPolicy: "owner_present", entryPolicy: "closed", handle: "@<tag>" }`, after confirming the device, Studio, and tag with the user. WhatsApp direct chats and groups both work. Web and iOS Connections edit each channel's tag and Agents. Treat messaging channels as a separate setup surface from external provider connections: a channel is where people message the Studio (the app itself, iMessage, WhatsApp); a connection is an account its agents use (GitHub).
- A channel's tag and Agents can also be changed through the connected Pronto tools with `channel.settings.update` (`payload.scope: "agent_route"` for its ordered Agents; `"studio_binding"` with `handle` for its tag, which keeps the channel's own `guestGroupPolicy` when none is given). Show the user the channel, Studio, and tag first; the old tag stops working in existing chats.
- To stop one Mac, retire that device's connection with `channel.settings.update` through the Pronto tools (`status: "retired"`). Never use `connection.disconnect` for messaging channels; it is provider-wide and is refused with `channel_provider_device_scoped`.
- The Channel Host's own credential is derived from the `s4` sign-in; never expect, request, or relay a second device code, and never copy credentials between the two. If a `channels host` command reports `authentication_required`, run `<s4-path> login --no-input` once and rerun it. If it reports `authentication_failed`, follow its remediation; on a signed-in Mac that is `<s4-path> channels host login`, which re-derives the host credential from the same sign-in without a new code. Stale host credentials are replaced automatically; only `channel_host_credential_stale` needs the owner to delete `studio-four-channel-host` items in Keychain Access. The device-code form of `s4 channels host login` is a fallback for the dedicated `s4-channel-host` executable with no `s4` sign-in and is not part of the ordinary flow.
- The always-on Messages process keeps a dedicated executable identity for macOS permissions, so Full Disk Access and Automation aren't granted to the everyday `s4` CLI. In groups, the verified sender is the actor and every participant is the disclosure audience, so an unresolved participant must fail closed before Studio discovery or agent execution.
- With `login --no-input --json`, the first stdout line is `data.status: "authorization_pending"` with the code and URL. Present it to the user at once; the command blocks until approval.
- `s4 update` on a Mac with a channel host re-derives the host credential and restarts the host. A host under signed maintenance may adopt the new release itself and exit right after the restart; launchd brings it back within about 30 seconds, so `launchctl list` can briefly show `-` for its PID. Check again after a minute before restarting it by hand with `launchctl kickstart gui/$(id -u)/com.studiofour.channel-host`.
- Requests the host could not finish are listed by `<s4-path> channels requests list`. `channels requests retry --event <id>` queues one retry of a proven pre-execution failure, and `channels requests manual-completed --event <id> --receipt <provider-id>` records one already answered by hand. `<s4-path> channels doctor` diagnoses the host without changing it.

## Failure behavior

Use the CLI error's `retryable` and `remediation` fields. Retry a retryable request once. Stop on release-verification, credential-store, authorization, or repeated service failures and report the safe remediation without printing raw headers, OAuth responses, or credentials.

`<s4-path> help --json` is self-describing; do not copy its evolving schemas into this skill.
